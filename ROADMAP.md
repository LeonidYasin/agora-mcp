# Roadmap

Обновлено по коду и наблюдаемым тестам 2026-10-11. Roadmap не означает разрешение сразу реализовать все пункты. Ядро проекта — обнаружение намерений; обмены могут продолжаться вне площадки.

## Stage 0 — текущий прототип

### Реализовано и проверено

- [x] Пять MCP-инструментов, stateless Streamable HTTP.
- [x] Пользовательская bearer-авторизация, хеши токенов, ownership guards.
- [x] PostgreSQL/pgvector, 1024-мерные embeddings, offer ↔ want, исключение собственного владельца.
- [x] Публичные карточки кандидатов и structuredContent, synapse/v0 match/item.
- [x] Ограничения ввода, 15-секундный embedding timeout, проверка вектора, безопасные ошибки.
- [x] CI build + unit tests + PostgreSQL smoke test; защищённая main и issue/PR workflow.
- [x] Отдельный systemd-сервис, существующий Caddy, `/agora/`, внешний Jina API.
- [x] Живой Notion: publication/listing/self exclusion/deactivation/negative cases.

### Что не следует считать уже доказанным

- [ ] Живой межпользовательский матч A/B и проверка чужой собственности: в CI проверяются, live-проверка ожидает второго токена.
- [ ] Установка на втором чистом VPS: новый runbook требует повторной проверки там.
- [ ] Качество RU/EN matching на размеченном наборе; role-prefix improvement — гипотеза.
- [ ] Публикация новой документации в GitHub Pages: файлы/CI ≠ live deployment.

## Ближайшие небольшие изменения

1. Завершить независимый двухпользовательский тест и зафиксировать исход без токенов.
2. Проверить fresh-VPS инструкцию на чистой машине, обновить её по наблюдениям.
3. Добавить управление актуальностью: редактирование, продление/отзыв, idempotency публикаций — через отдельные issues.
4. Добавить квоты/ограничение параллельных embedding-вызовов и план резервного копирования перед ростом.
5. Собрать небольшой RU/EN набор хороших и несовместимых пар; сравнить baseline/prefix, затем выбирать фильтры/порог.
6. Версионирование модели и процедура re-embedding перед любой её заменой.

## Stage 1 — качество обнаружения

Структурированные условия по реальной нише, допустимый пустой результат, порог релевантности по проверенному набору. Минимальный feedback — только если практика требует и есть понятные данные. Нельзя заранее выдавать cosine score за вероятность сделки.

## Stage 2 — улучшение ранжирования

Если накоплен достаточный сигнал полезности: candidate retrieval + лёгкий reranker, сохранённые реальные исходы. Сначала данные, затем алгоритм. Не вводить рейтинги на основании отсутствующих сигналов.

## Stage 3 — масштабирование по необходимости

Нагрузочные тесты, batch upsert, ANN recall при фильтрах, отдельные workers/retrieval infrastructure при измеренном ограничении. A2A может служить коммуникации после discovery; это не готовая текущая интеграция.

## Stage 4 — опциональные надстройки

Контакты по согласию, репутация/споры, институциональные функции или федерация только при доказанной потребности. Не обязательное условие полезного слоя обмена. Платёжный маркетплейс, P2P и управление сделками не входят в текущий scope.
