# Готовые маркетплейсы и взаимный подбор профилей для Agora

## Статус и границы

Расширение исследования к issue #12 / Draft PR #13. Только исследование и проектные
предложения: зависимости, методы, схема БД, OAuth, платежи и поведение Agora не
менялись. Ничего не устанавливалось и не запускалось на VPS. Чужой Python/CLI не
исполнялся, сервисам не передавались профили, резюме или секреты. GitHub CI,
автоматически возникающий при коммитах PR, не является VPS-проверкой.

Метод: публичный web-поиск для обнаружения кандидатов; официальные документы;
GitHub MCP для чтения закреплённых README, LICENSE, манифестов и выбранного кода.
Это не полный обход GitHub, аудит безопасности или проверка качества моделей.
README-обещания отмечены отдельно от прочитанного кода. Популярность не равна
качеству; примеры и научные реализации не называются production-продуктами.

## Четыре разных слоя

1. **Комнаты:** сообщения, история, участники, права, восстановление.
2. **Маркетплейс:** продавцы/покупатели, объявления, отклики, сделки и статусы.
3. **Семантический retrieval:** найти кандидатов по текстам/эмбеддингам и фильтрам.
4. **Reciprocal matching:** оценить пригодность A для B и B для A, затем порядок
   рекомендаций с учётом ограничений и доступности обеих сторон.

MCP — единый интерфейс доступа к этим слоям, а не замена хранилища или алгоритма.
Один endpoint не означает общий токен: владелец определяется серверной авторизацией.
Все варианты MCP-обёрток ниже — предложения, не обнаруженные готовые интеграции.

## A. Маркетплейсы, к которым можно добавить MCP

### A1. Mercur / Medusa — основной кандидат полного marketplace backend

Repository: [mercurjs/mercur](https://github.com/mercurjs/mercur).
Revision: `e63729233941a6ec23711469d69cbac364dc1662`.

[README, строки 35–85](https://github.com/mercurjs/mercur/blob/e63729233941a6ec23711469d69cbac364dc1662/README.md#L35-L85)
описывает headless API-first multi-vendor platform: onboarding продавцов, каталоги,
offers, комиссии и выплаты поверх Medusa. Указаны Node.js, PostgreSQL и Redis;
платёжные/поисковые интеграции требуют отдельных credentials. Это возможности,
заявленные проектом; обработчики API и их изоляция здесь не аудировались.

Прочитаны полный [MIT LICENSE](https://github.com/mercurjs/mercur/blob/e63729233941a6ec23711469d69cbac364dc1662/LICENSE)
и [package.json](https://github.com/mercurjs/mercur/blob/e63729233941a6ec23711469d69cbac364dc1662/package.json):
TypeScript/Medusa workspace, команды unit и HTTP integration tests. Их наличие не
доказывает запуск или успешный результат: CI Mercur в этом исследовании не проверен.

**Что переиспользовать:** vendor identity, catalog/offer lifecycle, заказы и админку,
если Agora действительно переходит к транзакционному рынку.
**Предлагаемый MCP:** поиск предложений, чтение карточки, публикация от своего vendor,
отклик/запрос; payment/order mutations только с отдельными правами и подтверждением.
**Не доказано:** готовые комнаты, взаимное matching профилей, спрос/want как
симметричная сущность, безопасный общий MCP endpoint. Товарный commerce тяжелее
короткой ленты услуг. Не устанавливать только ради хранения нескольких объявлений.

### A2. Cocorico — услуги/аренда, но существенная цена модернизации

Repository: [Cocolabs-SAS/cocorico](https://github.com/Cocolabs-SAS/cocorico).
Revision: `78814112258f6b400eff6191c58c6404efc4c0f8`.

Прочитаны [README](https://github.com/Cocolabs-SAS/cocorico/blob/78814112258f6b400eff6191c58c6404efc4c0f8/README.md),
[MIT LICENSE](https://github.com/Cocolabs-SAS/cocorico/blob/78814112258f6b400eff6191c58c6404efc4c0f8/LICENSE)
и [composer.json](https://github.com/Cocolabs-SAS/cocorico/blob/78814112258f6b400eff6191c58c6404efc4c0f8/composer.json).
Манифест version 0.15.1 требует PHP ^7.1, Symfony ^3.4, содержит ORM/ODM и
message-bundle. Публичное описание позиционирует проект как service/rental market.

**Польза:** предметная модель услуг/аренды ближе Agora, чем магазин физических товаров.
**Ограничение:** выбранная версия опирается на старый стек; текущая поддержка,
актуальные API и обновляемость зависимостей не подтверждены. Нельзя считать наличие
исходников готовым решением для нового публичного сервиса.
**Предлагаемый MCP:** адаптация доменных операций/контроллеров после их аудита,
не прямой доступ агента к ORM, БД или административным методам.

### A3. Shuup — дополнительный commerce-кандидат, пока не shortlist

[Официальный репозиторий](https://github.com/shuup/shuup) описывает Django/Python
E-Commerce Platform и OSL-3.0; имеется [раздел API](https://github.com/shuup/shuup/tree/master/doc/api).
Это web/README-проверка, без закреплённого аудита обработчиков. Не установлено, что
нужные multi-vendor-возможности и права входят именно в доступное ядро, а не расширения.
OSL-3.0 требует отдельного рассмотрения, её нельзя приравнивать к MIT.
**Решение:** держать в расширенном списке; прежде чем выбирать — проверить актуальную
поддержку, API продавца, удаление чужого объявления и лицензии всех нужных модулей.

### Что не выдаём за готовый open-source marketplace

[Sharetribe Go](https://github.com/sharetribe/sharetribe) прямо обозначен авторами
как **source-available**, no longer actively maintained, под Community Public License.
Современная облачная Sharetribe с API и открытый frontend-template не доказывают
наличие открытого self-hosted backend. Не включать в MIT/Apache shortlist по одному
упоминанию GitHub. Headless commerce вообще не равен multi-vendor marketplace.

## B. Движки эмбеддингов и ранжирования

### B1. Sentence Transformers + pgvector — компоненты базового retrieval

[Sentence Transformers: semantic search](https://sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)
документирует asymmetric query/document encoding и retrieve → cross-encoder rerank.
Это готовые инструменты поиска и ранжирования, не платформа профилей и не готовый
алгоритм взаимной совместимости. Конкретную модель и её лицензию, русский язык,
длину текста и качество нужно выбирать и проверять отдельно от лицензии библиотеки.

[pgvector](https://github.com/pgvector/pgvector) документирует exact/approximate
nearest neighbours, фильтры и hybrid search с Postgres full-text. ANN обменивает
полноту поиска ближайших векторов на скорость; фильтры могут уменьшить число
результатов. Сравнение ANN с exact нужно делать на одном корпусе и одной модели.
Даже exact retrieval не гарантирует нахождения всех концептуально подходящих людей:
он точен относительно заданных векторов, метрики и доступных данных, не реальности.

**Польза для Agora:** переиспользовать retrieval/reranking, а не писать собственный
векторный индекс. Это вариант для DB-направления, не новая зависимость memory-MVP.

### B2. Metarank — отдельный сервис ranking и feedback

Repository: [metarank/metarank](https://github.com/metarank/metarank).
Revision: `b9c719fedba67b762476ee719570915f4768b6b9`.

Прочитаны [README](https://github.com/metarank/metarank/blob/b9c719fedba67b762476ee719570915f4768b6b9/README.md),
полный [Apache-2.0 LICENSE](https://github.com/metarank/metarank/blob/b9c719fedba67b762476ee719570915f4768b6b9/LICENSE)
и [semantic model docs](https://github.com/metarank/metarank/blob/b9c719fedba67b762476ee719570915f4768b6b9/doc/configuration/recommendations/semantic.md).
Документы описывают rank/feedback API, learning-to-rank, bi-/cross-encoder features;
semantic similarity может работать без пользовательского feedback. Указаны ограничения
ONNX-моделей и импорт готовых векторов CSV. Redis предусмотрен для состояния;
в демонстрации используется memory store. Заявленную задержку не измеряли.

**Польза:** позже учиться на осмысленных откликах/сделках, а не только cosine score.
**Не готово из коробки:** двустороннее согласие, лимиты доступности, marketplace и
безопасная MCP-авторизация. Оптимизировать только CTR для рынка может быть неверной
целью: клики не равны полезным договорённостям.

## C. Найм и дейтинг: прямые аналоги подбора

### C1. CyberAgentAILab/FairReciprocalRecommendation — наиболее полезный алгоритмический аналог

Revision: `28904826edf2319e898586beb99c80375f9310b4`.

[README](https://github.com/CyberAgentAILab/FairReciprocalRecommendation/blob/28904826edf2319e898586beb99c80375f9310b4/README.md)
связывает код с RecSys 2024 и working paper 2025 о matching markets, fairness и match
rates. Полный [MIT LICENSE](https://github.com/CyberAgentAILab/FairReciprocalRecommendation/blob/28904826edf2319e898586beb99c80375f9310b4/LICENSE)
прочитан. Это воспроизводимый исследовательский код, не готовый web/MCP-сервис.

**Проверено в коде:**
- [src/prod.py](https://github.com/CyberAgentAILab/FairReciprocalRecommendation/blob/28904826edf2319e898586beb99c80375f9310b4/src/prod.py)
  принимает две матрицы направленных предпочтений и умножает A→B на транспонированную B→A.
- [src/alternate_fw.py](https://github.com/CyberAgentAILab/FairReciprocalRecommendation/blob/28904826edf2319e898586beb99c80375f9310b4/src/alternate_fw.py)
  содержит SW/NSW optimization, CVXPY и позиционные examination vectors. В реализации
  создаются плотные трёхмерные массивы; применение ко всему большому рынку без
  ограничения кандидатов и проверки ресурсов недопустимо.

**Польза:** не ограничиваться односторонней похожестью резюме/вакансии; учитывать
обе стороны и распределение показов. **Чего нет:** превращения текста в достоверные
предпочтения, production identity, профильного API, хранилища и гарантий качества
на Agora. Алгоритмы не запускались. Социальные/экономические предпочтения нельзя
просто заменить произвольным cosine score и назвать вероятностью сделки.

### C2. jackvandervall/resume-job-matcher — понятный baseline найма, не open-source hh

Revision: `4a1974f3e57070b30950e07fdddd9bd56d6cc006`.
Прочитаны README, полный MIT LICENSE,
[app.py](https://github.com/jackvandervall/resume-job-matcher/blob/4a1974f3e57070b30950e07fdddd9bd56d6cc006/app.py)
и [embeddings_jobs.py](https://github.com/jackvandervall/resume-job-matcher/blob/4a1974f3e57070b30950e07fdddd9bd56d6cc006/src/embeddings/embeddings_jobs.py).

В коде: all-mpnet-base-v2, нормализованные embeddings, cosine similarity,
поиск по заранее подготовленным numpy-массивам, Streamlit single/batch/search UI.
Текст при подготовке ограничивается; обработка длинных резюме требует проверки.
Пороговые подписи Strong/Moderate Match заданы в коде; калибровка на реальных
исходах не показана в прочитанных файлах. Отображаемые проценты similarity нельзя
принимать за вероятность найма или пригодности.

**Польза:** прозрачный baseline и пример pipeline профилей. **Не подтверждены:**
production multi-user API, reciprocal preferences, строгие фильтры зарплаты/времени,
валидированное качество русских текстов, безопасность персональных данных.
Не заменяет hh, ATS или проверенный сервис подбора.

### C3. RECON и другие dating-проекты — методологические ссылки

[RECON: reciprocal recommender](https://dl.acm.org/doi/10.1145/1864708.1864787)
объясняет постановку, где люди одновременно субъекты и объекты рекомендаций.
[asinghvi92/Dating-Recommendation-System](https://github.com/asinghvi92/Dating-Recommendation-System)

для копирования или эксплуатации. Данные дейтинга/найма не импортировать без
законного основания. Никаких утверждений о внутреннем алгоритме hh не делается.

## D. Предлагаемый pipeline Agora — не реализовано

1. Разделить поля профиля: **что предлагаю**, **что ищу**, **обязательные условия**,
   **предпочтения**, **доступность**, **видимость/согласие**. Не один общий вектор человека.
2. Применить permissions и жёсткие условия: язык, бюджет/валюта, сроки, география,
   формат работы, активность объявления, блокировки. Отсутствие поля — unknown, не match.
3. Получить кандидатов по потребность(A) ↔ предложение(B), используя keyword +
   embedding retrieval. Сохранять model/version/field-role для совместимости векторов.
4. Переранжировать пары по содержательной пригодности, не только схожести слов.
5. Оценить два направления: удовлетворяет ли B запросу A и подходит ли A условиям B.
   В денежной сделке обратное направление может быть бюджет/время/условия, а не
   встречная услуга: рынок не обязательно бартер.
6. Агрегировать обе оценки как проверяемый baseline (например, минимум или
   геометрическое среднее неотрицательных нормированных оценок); низкую пригодность
   одной стороны нельзя компенсировать высокой другой. Это проектная гипотеза,
   не калиброванная вероятность и не эквивалент всех алгоритмов CyberAgent.
7. Учитывать capacity и exposure: не отправлять все запросы одному популярному
   исполнителю. SW/NSW-подходы исследовать после появления достаточного feedback.
8. Вернуть причины, несовпадения, неизвестные условия и границы поиска. Контакт,
   публикация и сделка — отдельные действия с правами/согласием, не автоматический
   побочный эффект рекомендации.

Для проверки собрать согласованную человеком контрольную выборку: подходящие,
неподходящие и сложные пары (отрицания, роль «ищу» против «умею», языки, устаревшие
объявления, несовместимые условия). Сравнить keyword, embeddings и reranking;
оценивать candidate recall@K, ranking relevance, долю нарушений обязательных условий,
взаимно принятые контакты, нагрузку/стоимость и распределение показов. Это план,
не выполненный benchmark. Не использовать защищённые/чувствительные характеристики
для дискриминационного ранжирования; приватные поля не должны утекать в объяснения.

## E. Решение по переиспользованию

- **Нужен полный commerce:** первым проверить API/tenant isolation Mercur, а не
  писать заказы, продавцов и комиссии самостоятельно. Для short-feed MVP это может
  быть избыточно. Платежи не входят в текущую реализацию.
- **Нужны только комнаты:** Matrix/Prosody — другой слой, не замена marketplace
  или reciprocal matching. Готовый backend не делает любой MCP-адаптер безопасным.
- **Нужен semantic matching:** сравнить готовый retrieval/rerank pipeline и простой
  двусторонний baseline; CyberAgent — источник алгоритмов, Metarank — кандидат
  отдельного ranking/feedback сервиса. Не подключать все системы одновременно.
- **Пока не выбран production stack:** стоимость поддержки, лицензии моделей и
  зависимостей, актуальные CVE, тесты изоляции, восстановление и качество русских
  профилей ещё требуют проверки. Ни полнота GitHub-поиска, ни спрос не доказаны.

Следующая исследовательская развилка: Mercur API-spike против лёгкого market backend;
независимо от неё — офлайн сравнение retrieval и reciprocal ranking на согласованных
тестовых данных. Любое выполнение на VPS требует отдельного подтверждения владельца
и предусмотренного секретного подтверждения. Текущий memory-прототип не объявлен
production-архитектурой и не развёрнут этим исследованием.
