# Проверка русского подбора до выбора бесплатной модели

## Результат этого изменения

Issue #14: добавлен полностью offline evaluation kit, а не новый deployed matcher.
Он подключён к существующему `npm test`, не вызывает embeddings, не использует
БД, сеть или секреты и не меняет MCP tools. Зависимости не добавлены.

Код: `mcp-server/test/support/matching-evaluation.mjs`.
Корпус: `mcp-server/test/fixtures/russian-matching.mjs`.
Проверки: `mcp-server/test/matching-evaluation.test.mjs`.

Обычный GitHub CI собирает сервер и выполняет эти тесты вместе с существующими.
Для этой работы не требуется запуск на VPS. Факт зелёного CI нужно проверять для
конкретного SHA; наличие файлов или passing старого SHA — не результат проверки.

## Что измеряем и чего не скрываем

Синтетические примеры составлены разработчиком, не взяты из реальных профилей.
Они проверяют точный запрос, синонимы, отрицание, ограничение цены, очную географию,
обратное направление offer → want, нормализацию ё/е и допустимый пустой результат.
Это небольшой smoke corpus, не независимый benchmark и не оценка всех русских
текстов. RU/EN, опечатки, омонимы, prompt injection, длинные тексты и сложные
составные ограничения требуют расширения корпуса и отдельного review разметки.

Lexical baseline — Jaccard по точным словам, без ручных синонимов и стемминга.
Тесты намеренно фиксируют его **известные неправильные первые результаты**:

| Пример | Нужный смысл | Ошибка baseline, которую тест не выдаёт за успех |
| --- | --- | --- |
| Врач для ребёнка | Педиатр | Книги для ребёнка из-за общих слов |
| Передержка кошки | Человек, принимающий кота | Объявление с отказом принимать кошек |
| Ремонт до 3000 рублей | Починка за 2000 | Ремонт от 9000 |
| Очно в Казани | Настройщик в Казани | Та же услуга в Москве |

Прохождение characterization-теста означает воспроизводимость этого ограничения,
**не** хороший semantic matching. Корпус нужно использовать для сравнения будущего
multilingual adapter; нельзя объявлять качественную модель только по зелёному CI.
Денежный запрос допустим: покупатель не обязан предлагать вторую услугу для бартера.

## Контракт следующего адаптера

`evaluateRanking` передаёт ranker только query и неизменяемый eligible pool:
противоположный тип, другой владелец, та же комната, активность и TTL. Разметка
relevant/incompatible в ranker не передаётся. Production-источник должен отдельно
проверить авторизацию владельца: эти offline gates не являются auth boundary.
Поля цены и географии здесь остаются текстом, не притворяются готовыми SQL-фильтрами.

Adapter возвращает упорядоченный массив `{id, score}`. Harness проверяет весь
ответ до усечения: unknown/excluded IDs, дубли и нечисловые/бесконечные score
отклоняются. Порядок сохраняется; score может быть отрицательным и не называется
вероятностью. Пустой ответ допустим; ошибка провайдера не превращается в успешный
пустой ответ. Выдача явно ограничена `supplied_eligible_pool`, exhaustive=false.

Это сравнение сторон объявления, а не полноценная двусторонняя оценка интересов
людей. Взаимная приемлемость условий и reciprocal ranking требуют отдельной модели
предпочтений; cosine/Jaccard и наличие двух типов этого не заменяют. Никакие
профили, embeddings и ответы внешнего провайдера в данном PR не получены.

## Следующий рубеж решения

Предварительные инфраструктурные кандидаты исследованы отдельно в PR #13:
Cloudflare Workers/D1/Vectorize/Workers AI и Supabase/Postgres с отдельной
multilingual моделью. Здесь платформа не выбирается и продукт на неё не переносится.

1. Review синтетической разметки и добавление владельцем независимых обезличенных
   примеров. До согласования не передавать реальные данные провайдерам.
2. Согласовать один внешний Free adapter и условия обработки данных, затем сравнить
   его на том же корпусе без доступа к меткам. Цена/география/отрицание требуют
   структурированных ограничений или дополнительной проверки, не только embeddings.
3. Проверить нулевой расход, quota failure, экспорт и восстановление, MCP клиента
   с двумя владельцами. Это отдельные live-проверки, здесь они не выполнены.
4. Зафиксировать ADR. Не менять работающий Stage 0, не объединять OAuth PR #11 и
   не деплоить по факту успешного offline CI.
